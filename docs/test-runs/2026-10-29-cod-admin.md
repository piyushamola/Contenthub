## Coverage

- Actual standard Shopify gateway identifies pending COD; generic pending bank
  transfers, custom lookalike gateways and combined gateways are not COD.
- COD amount includes reconciled discounted items, shipping and applicable tax;
  included tax is not counted twice. Mixed carts, partial payments, malformed or
  missing financial fields, refunds/cancellations are blocked.
- Paid orders remain prepaid, including a formerly COD order paid before submission.
- Fresh Shopify Admin API money/gateway data is normalized through the same rules.
- `orders/create`, paid/updated events, repeated and concurrent delivery and stale
  creates retain one record/reference. Same-time stale pending events do not
  downgrade paid state. Existing uncertainty/lease/reconciliation tests remain.
- Artwork corrections bind to a source revision, preserve financial/product/
  delivery inputs, validate trusted hosts and decoded dimensions, and require a
  validation state before queueing. Validation performs no provider POST.
- Pause revokes a leased worker before intent. In the real PostgreSQL/SQLite race,
  exactly one of pause or intent wins. Post-intent correction/pause is denied.
- Missing/invalid admin authentication and ordinary Content API credentials are
  denied. Real admin RBAC separates read, notes and operational actions.
- Search, pagination, payment filtering and private projections work. Raw Content
  Manager access and public audit CRUD are denied. Direct state/digest/financial/
  provider edits are not supported by the admin actions.
- Notes/actions record actor/time/reason and hashes/state changes. An audit write
  failure rolls back the notes change. Stale admin revisions after a Shopify
  update are rejected. Historical prepaid records remain readable; original
  references/snapshots/submission history are not regenerated.
- Real admin browser journeys cover login, responsive navigation, searching and
  filtering, notes, pause, artwork correction and resume-to-validation.
- COD provider tracking must report the expected payment mode and collectible
  amount before Shopify fulfillment. Existing exact-line/quantity/AWB checks remain.

Catalog cases: **POD-07–17**.

1. The initial COD test reproduced missing support: **3 passed / 4 failed** before
   implementation. The intended COD cases then passed.
2. Initial browser gate: **12 passed / 3 failed** because Strapi's required-field
   label did not match an exact login-label locator. The test now uses the
   rendered accessible textbox name and password label.
3. A focused browser run exposed that Strapi also owns a global live status
   region. The assertion now selects this view's status inside its main content.
4. The next combined gate had **14 passed / 1 failed**: mobile Strapi moves plugin
   links into its Menu. The journey now opens that menu on mobile.
5. The final combined gate passed **15/15** with zero retries. No checks were
   skipped or assertions weakened to hide a failure.
6. Two added compatibility regressions reproduced false source/product changes
   when database JSON fields were reordered. Comparisons now use structural
   equality. Stored digests, references and design-code hashing are unchanged.
   The unit/type/stack checks were rerun after this fix.
7. One subsequent stack launch timed out in the build-time TypeScript stage
   before executing any tests. Standalone typechecking still passed. The normal
   isolated runner was rerun without increasing its timeout, adding retries or
   disabling checks.
